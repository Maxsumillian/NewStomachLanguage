POLYMORPHISM / VARIABLE ARCHITECTURE (DESIGN NOTES)
===================================================

1. CORE VARIABLE DESIGN
-----------------------

StomachLang variables are NOT traditional data containers.

Instead:
- Each variable ONLY stores a memory address
- All actual data lives inside CPU-controlled memory
- The CPU resolves values using these addresses

Example:
Calories x = 100;

Internally:
- x does NOT store "100"
- x stores a memory address
- CPU retrieves value from memory using that address


2. STATIC MEMORY TRACKING SYSTEM
---------------------------------

A static system tracks variable creation.

- Every new variable increments a global/static counter
- Each variable is assigned a unique memory address
- The CPU uses this address to access stored values

This enables:
- centralized memory control
- predictable allocation
- CPU-managed execution model


3. INHERITANCE-BASED TYPE SYSTEM (ACTUAL IMPLEMENTATION)
--------------------------------------------------------

The system uses inheritance to define variable types:

- Edible   (base or related type)
- Calories (derived type)
- Foods    (derived type)

Each type defines:
- valid input types (int, string, bool)
- behavior in CPU operations
- operator overload behavior

This was used as the main polymorphism system.


4. DESIGN INSIGHT (REFLECTION)
------------------------------

I could have used templates to optimize the chaining of commands.

Example:
- Calories would return Calories
- Variables would return Variables

But at the time, I did not know about templates, so I made the return type generic by returning a base Variable class.

Because of this, each child class needed a constructor that accepts a Variable as a parameter.
This constructor would then transfer (“swap”) the data into the correct memory location for that specific type.

Also, although a constructor-based type distinction system was possible, it would not have allowed me to define variable types as separate class definitions.

Instead, all variables would effectively become one general “Variable system” acting as a central controller, which was not the design I wanted.

Using inheritance and separate child classes was therefore necessary to achieve distinct type definitions such as:

Calories myCal = 10;


5. VARIABLE STORAGE MODEL
------------------------

A key design feature:

- Variables do NOT store raw data
- They only store memory addresses
- All data access is routed through the CPU

This creates a strict separation between:
- variable identity (address)
- variable value (CPU memory)


6. CHAINED EXPRESSIONS + RETURN BEHAVIOR
----------------------------------------

Expression chaining is supported:

Example:
Calories result = a + b + c;

Design behavior:
- operator+ returns a Variable object
- results are stored in CPU-managed temporary memory
- original variables remain unchanged

This allows:
- safe chaining
- non-destructive operations
- CPU-controlled evaluation flow


7. CPU-BASED CONVERSION/ARITHMIC SYSTEM
------------------------------
For my comparison operators, I implemented them as friend functions inside my language system class.

These functions retrieve values from the CPU (via memory addresses) and then perform the comparison in C++.

I could have moved all of this logic directly into the CPU, but that would require adding many additional primitive comparison functions, which would significantly increase complexity.

I am currently exploring templates to reduce repetition, but depending on how operator overloading behaves, it may not be worth it because I would still end up creating multiple specialized cases. so helper functions may be better

For now, I am satisfied with the current approach:
- data is retrieved from memory
- then compared using primitive C++ operations

Alternatively, I could fully delegate comparisons to the CPU and have it return the result, but that feels somewhat redundant given the current design already achieves the same outcome.


For arithmetic operators, all operations are handled inside the CPU even primitive.

I also created a template helper for arithmetic operations between variables, which works for most cases.

However, addition is treated as a special case because it supports both:
- numeric addition
- string concatenation

Because of this dual behavior, addition was excluded from the generic arithmetic template helper to keep the implementation simpler and more controlled.

8. SUMMARY
----------

StomachLang variables behave as:

- memory-address wrappers
- CPU-resolved values
- inheritance-based polymorphic types
- non-owning references to stored data

The system prioritizes:
- CPU-controlled execution
- operator overloading for syntax
- inheritance for type behavior

POLYMORPHISM / DESIGN REFLECTION
--------------------------------

After completing the system, an important realization was made:

Inheritance was not strictly required for the variable system.

Instead of using an inheritance hierarchy for Edible, Calories, and Foods,
the same behavior could have been achieved using:

- a single base Variable class
- multiple overloaded constructors
- different constructor signatures for each input type

Example idea:
Variable(int)
Variable(const char*)
Variable(bool)

This approach could have:
- simplified the overall architecture
- reduced complexity from inheritance chains
- removed the need for virtual functions
- made type handling more direct at construction time

However, the current implementation still uses inheritance to define type behavior.

So while inheritance worked, it introduced additional complexity that could have been avoided with a constructor-overloading-based design. however this way creates a god varibels capable of storing all types of data and isnt defined like

Calories myCal = 10;

and isntead can just be

Varible myVar = 10;

- memory is properly initialized after full object construction

FEATURES
========================================================================================================================

1. CPU-BASED EXPRESSION EVALUATION (TEMP VARIABLES)
---------------------------------------------------

The CPU supports chained expressions such as:

Variable var = var1 + var2 + var3;

To support this, operator+ returns a Variable instead of modifying operands.

IMPORTANT DESIGN RULE:
- Original variables (var1, var2, var3) are NOT modified during operations.
- This prevents unintended mutation during chained expressions.

TEMP VARIABLE SYSTEM:
- The CPU generates temporary values for intermediate results.
- These temporary values are stored in a reserved memory slot (slot 0).
- Slot 0 is not part of normal user-accessible memory.

Example:
var1 + var2 + var3
-> CPU creates temporary chain result in slot 0
-> Final result is returned as a Variable


2. CHAINED CONSTRUCTION SYSTEM
--------------------------------

Expressions like:

Variable var = var1 + var2 + var3;

are resolved through a constructor system.

The CPU produces a temporary object of type:
FatherVariable

This object is then passed into:

Variable(FatherVariable var);

This allows:
- chained expression evaluation
- safe temporary result handling
- proper conversion into child types

This mechanism enables full expression chaining without breaking variable state.


3. CPU PARSER / DECODER SYSTEM
--------------------------------

The CPU includes a parser/decoder system that processes instruction strings.

- Inputs are split using ":" as a delimiter
- Parsed segments are interpreted as CPU instructions
- Enables structured execution of complex expressions


4. MULTI-TYPE OPERATION SUPPORT
--------------------------------

The CPU supports automatic type-aware operations:

INTEGER (Calories):
- Performs arithmetic addition, subtraction, multiplication, etc.

STRING (Foods):
- Performs concatenation using + operator

BOOLEAN (Edible):
- Performs logical comparisons and boolean operations

The CPU determines behavior dynamically based on operand types.


5. OBJECT-BASED VARIABLE SYSTEM
--------------------------------

All variables are implemented as C++ classes.

This allows:
- operator overloading
- CPU-controlled behavior
- memory tracking per variable
- consistent syntax with traditional programming languages


6. INHERITANCE + CONSTRUCTOR BEHAVIOR
--------------------------------------

Due to C++ constructor rules:

- Parent constructors are called before child constructors

To properly initialize runtime behavior:
- virtual functions are used inside constructors
- this allows correct datatype configuration after inheritance setup

This ensures that derived types correctly register their CPU behavior.


7. COMPARISON SYSTEM
--------------------

Comparison operators have been implemented for all three data types:

- Calories (int comparisons)
- Foods (string comparisons)
- Edible (boolean comparisons)

Supported operators:
==   !=   >   >=   <   <=

All comparisons are processed through CPU-controlled evaluation logic.


8. MEMORY MANAGEMENT MODEL (TEMP SYSTEM)
----------------------------------------

- Temporary results are stored in reserved CPU memory (slot 0)
- No garbage collection is currently implemented
- Temporary values are overwritten per expression evaluation

This system allows safe chained expression evaluation without modifying source variables.
