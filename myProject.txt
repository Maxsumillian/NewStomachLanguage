This is my second attempt at this project.

Originally, I built a version using maps and a symbol table system.
Each variable stored an address and was retrieved dynamically.

That system became extremely complex because:
- variables didn’t clearly track memory location
- ordering memory required tracking insertion history
- required additional structures like double arrays for lookup

On my second attempt, I simplified the design by storing memory addresses directly inside variables, which made the system significantly easier to manage.


========================================================================================================================
FINAL ARCHITECTURE OVERVIEW
========================================================================================================================

1. CORE DESIGN IDEA
-------------------

StomachLang is a CPU-driven virtual language system.

Key idea:
- Variables do NOT store values
- Variables ONLY store memory addresses
- CPU is responsible for all data access and computation


2. VARIABLE SYSTEM
------------------

All variables behave like lightweight memory references.

Example:
Calories x = 100;

Internally:
- x holds an address
- value is stored in CPU-managed memory
- CPU resolves value at runtime


3. POLYMORPHISM / TYPE SYSTEM (INHERITANCE BASED)
-------------------------------------------------

The system uses inheritance for type behavior:

- Edible
- Calories
- Foods

Each type defines:
- valid input type
- operator behavior
- CPU interaction rules


4. EXPRESSION EVALUATION MODEL
------------------------------

Expressions are evaluated using the CPU:

Variable result = a + b + c;

Execution:
- operator+ returns a Variable object
- CPU stores intermediate results in temporary memory (slot 0)
- original variables are never modified


5. TEMPORARY MEMORY SYSTEM
--------------------------

- CPU uses reserved memory slot (slot 0)
- stores intermediate computation results
- overwritten per expression
- no garbage collection currently implemented


6. CHAINING SYSTEM (FATHER VARIABLE)
------------------------------------

Before templates were understood, chaining was implemented using:

- operator+ returns a generic Variable type
- a FatherVariable system holds temporary results
- child constructors convert FatherVariable into correct type

This allows:
- chained expressions
- safe intermediate evaluation
- controlled memory assignment


7. CPU ROLE
-----------

The CPU is responsible for:

- arithmetic operations
- comparisons
- string concatenation
- memory access
- expression evaluation

Operators act only as syntax triggers.


8. DESIGN INSIGHTS (REFLECTION)
------------------------------

- Inheritance was used for polymorphism, but could have been replaced with constructor overloading
- Templates could significantly improve chaining and type handling if redesigning
- Addition is treated as a special case due to string concatenation behavior
- CPU-centric architecture simplifies variable behavior but increases system responsibility


9. KNOWN LIMITATIONS
--------------------

- No garbage collection
- Limited type system (int/string/bool only)
- CPU holds most complexity
- Header/function separation issues during development
- Debugging required careful memory tracking


10. FINAL SUMMARY
-----------------

StomachLang is a CPU-driven virtual language system where:

- variables are memory addresses
- CPU handles all computation
- inheritance defines type behavior
- operator overloading provides syntax layer
- temporary memory enables expression chaining

It behaves like a simplified interpreter / virtual machine built in C++.


11. AI USAGE / DEVELOPMENT SUPPORT
-----------------------------------

During development, AI tools were used as a supporting resource in the following ways:

1. STRUCTURE SUPPORT
--------------------
AI was initially used to help define and organize the overall structure of the project.

This included:
- breaking the system into CPU / Memory / Language layers
- helping identify major components of the architecture
- clarifying how a virtual language system could be structured in C++

This was used as a planning aid, not as direct implementation.

2. DEBUGGING ASSISTANCE
-----------------------
AI was heavily used during debugging to understand and resolve issues such as:

- operator overloading compilation errors
- header vs cpp function definition issues
- template-related compilation constraints
- inheritance and constructor initialization order problems
- memory/address handling mistakes
- CPU accumulator state bugs

3. COMMON BUG TYPES ENCOUNTERED
-------------------------------

The most frequent issues were:

- function declaration vs definition mismatches (header file issues)
- template instantiation errors
- incorrect type resolution in overloaded operators
- memory not updating correctly after CPU operations
- constructor order causing incorrect initialization state
- runtime type mismatches between CPU and variable system

4. HOW AI WAS USED (IMPORTANT CLARIFICATION)
-------------------------------------------
AI was NOT used to generate the final system.

Instead, it was used to:
- explain compiler errors
- suggest debugging directions
- clarify C++ language behavior (especially templates and inheritance)
- help reason through complex architecture decisions

All core system design decisions and implementation logic were developed manually through iteration and testing.
